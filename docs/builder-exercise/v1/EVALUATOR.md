# Evaluator protocol

Do not hand the builder a completed reference harness or core-source walkthrough.
Reuse verification tooling to check their output; providing implementation code is
assistance and changes the result classification. This package has not been run.

## Freeze and entry gate

- Verify `freeze.json`; record package ID, baseline commit and verification output.
  Record the builder's experience and any prior access to this code or research.
- Seal agreed intake/task, selected merchant/license adapter, track, documentation
  set and consent/actions with a hash before the measured attempt. No arbitrary
  time threshold or development-speed ratio. Keep credentials out of this record.
- Ready-runtime gate: check pinned tools and image/artifact receipts, loopback RPC
  version/genesis, explicit SBF feature override and two-node runtime health. Record
  setup time/help/cache state. A stopped service or missing cache is an environment
  blocker, not evidence of failed SDK abstraction. Do not reset a reference ledger.
- Assign private fresh paths and explicit synthetic local owner/admin roles. Builder
  deploys their own original policy after build; readiness does not supply a completed
  customer policy or reused initialized quota. Successful deployment must include real
  initializer callback, all loaded ELF matches and both uploaded circuit/interface checks.

## Acceptance and evidence

For each row record timestamp, outcome, evidence path/hash, assistance and evidence
class: host, simulated, real local validator, actual two-node local computation,
or retained archive check. These are not interchangeable. Unexecuted rows remain
unqualified, even if a prior reference application passed a similar case.

| Gate | Evidence required |
| --- | --- |
| Original policy/application | Builder-owned source/schema/tests and generated release identity; original state-dependent logic, no core edit or template/constants-only answer. Retain customer source snapshot and build provenance. |
| Authored tests | Acceptance/denial, exact boundary, zero, underflow, reserve multiply/add overflow, purchase-count overflow, preserved denial state, native amount/binding failure. Tests execute supported compiler IR; report only host guarantees. |
| Genuine private decision | Actual immutable Job and correctly bound authenticated Arcium callback, fresh runtime MXE keys, matched deployed circuit/release. No fixture keys, preauthorized permits or injected verified contexts. |
| Exact paid effect | Native transfer plus consumed bound permit, full encrypted state successor/version and exact buyer/SKU (or product/expiry) effect in one landed transaction. Check real owner signatures, message/ALT/native binding and account evidence. Auth callback alone does not pass. |
| Funded denial | Valid native funding/proofs with policy denial; no paid effect or business-state consumption. Report admission-counter changes separately from business-state changes. |
| Stale authorization | Two separately funded native sources share a business-state predecessor. Prepare/admit sequentially to respect admission counter changes. Commit A, retain B unchanged; B is stale and cannot settle that predecessor. Distinguish SDK refusal, simulation error and landed rejection; do not call one another. |
| Fresh computation | Explicit owner/admin consent, new Job/permit/nonce and operation after inspecting stale/unpaid state; real new callback and honest current decision. No automatic retry or changed old signed bytes. |
| Compatible purchase | Separately approved current-state operation that actually pays and issues its distinct effect; preserves earlier business identity semantics. |
| Atomic rejection | Evaluator uses existing post-native failure qualification machinery where applicable; retain the actual landed rejection and unchanged native/quota/effect account bytes. If only simulation is obtained, record that narrower result. Never provide a fault-control bypass as a product API. |
| Restart/exact recovery | Separate keyless process via generated session; same plan, approval directory, signature/hash and attempts; no new signer/blockhash/query/nonce. Require read-only recovery before any explicit resubmit. Record staging interruption points actually exercised. |
| Receipt/account outage | Selective test-only HTTP faults at receipt/status/account boundaries, not fabricated account/receipt success. Receipt outage can coexist with committed accounts; both unavailable stays unresolved; contradictory evidence remains hard failure. No broadcasts during uncertainty. |
| Fresh receipt restoration | Before pruning of an otherwise-useful fresh paid operation, restore RPC and obtain the same retained signature's exact receipt. Separate processes, same wire/hash, no resubmission/replacement. If already pruned, leave this gate unqualified rather than resetting or injecting history. |
| Presentation | Separately show committed effect, delivery/receipt availability and current entitlement use. Expired license stays historically paid but unusable; it cannot renew access or authorize another payment. Merchant issuance has no license TTL. |
| Isolation | Check the builder deployment's release/schema/domain/MXE identity and that reference instance/program/account identities were not reused. Reuse existing wrong-domain/release corruption checks as evaluator tests; label host/archive checks rather than claiming fresh live cross-instance isolation. |

For the artificial fallback, evaluator-only synthetic state may be
`remaining=100, reserve_floor=20, purchases=0, reserve_step=10`. Label these as
**test-observer disclosures**, not public product balances or live private decryption.
One useful sequence is A40 and B40 authorized against business state `[100,20,0,10]`
using distinct funded sources. A pays, leaving `[60,20,1,10]`; old B is stale. A fresh
B40 is denied despite sufficient funding because remaining20 would fall below30.
A fresh compatible20 may pay, leaving `[40,20,2,10]`. These are mathematical expected
outcomes, not newly executed evidence. Builder still authors policy/tests/integration;
do not give them an existing implementation of this sequence as their application.

Qualification helpers may be inspected/adapted by the evaluator: deployment's loaded
program/circuit checks; `examples/policies/qualification/{evidence,archive}.mjs`;
`examples/license-session/receipt-outage.mjs` for fresh-process transport-fault boundaries;
prior licensed transition verifiers for the **license** adapter only. Do not run the
license-specific crash harness blindly against a merchant/custom policy or reuse its
hardcoded amounts as proof. Write any required evaluator adaptation separately and log
it as evaluator work, not builder productivity. A checker may not synthesize a permit,
verified context, decision or signature. Check the actual loaded ELF after source changes.

## Stop rule and support

Record all interventions in `run-record.json`: time, category, initiator, question,
answer/code/docs, whether needed for completion, and outcome. Categories:
`environment-setup`, `existing-doc-navigation`, `missing-behavior-explanation`,
`code-writing-or-fix`. Voluntary core-source inspection is separately logged friction;
it is not automatically failure unless an undocumented dependency/workaround is required.

A required core edit or undocumented signer/journal workaround ends the scoped unaided
attempt as failed. Preserve its freeze, artifacts and outcome. Any repaired continuation
gets a separate run ID, assistance label and (if changed) new baseline/package ID.
Any intervention-dependent completion is assisted, even a small explanation or fix.
Prearranged environment setup defines the ready-runtime track; log it without pretending
it was clean-machine installation. Report unanticipated environment blockers separately.
Never hide failures by deleting an instance, rebuilding in place or reclassifying a
later assisted run as the earlier unaided one.

Record milestone timestamps for intake/freeze, environment ready, first passing rule
tests, build, deployment, first authentic decision, first paid effect, denial/stale,
restart/recovery and all applicable final gates. Record active builder time, evaluator
work, machine waiting and blocked time separately. Report counters/costs for native
provisioning, compiler/upload, queue, callback, settlement and recovery separately.
Do not compare source-size ratios or partial upstream implementations as effort parity.

Allowed conclusion: “usable in this exercise,” with exact track, assistance and passed/
unqualified gates. No demand, retention, pricing, speed improvement, customer preference,
external integration commitment, independent-operator or production-security claim.
If no outside builder has run it, the result is “package prepared; external test pending.”
